1

How a line is validated

Every marketplace ships a vendor price. The engine computes our price from the item's MRP and the marketplace's margin, then compares. If they agree (within tolerance) the line is OK; if not, it's a MISMATCH for you to decide on.

Landing basis

Used by Blinkit, Flipkart, Myntra… The check is pre-GST.

Our Landing = MRP × margin%
Example — MRP ₹500, margin 70%
→ Our Landing = 500 × 0.70 = ₹350
Vendor landing ₹350 → OK · ₹380 → MISMATCH (diff ₹30)
Cost basis

Used by RK, Blink, Reliance… The check is post-GST (cost price).

Our CP = MRP × margin% ÷ (1 + GST)
Example — MRP ₹500, margin 70%, GST 18%
→ Our CP = 500 × 0.70 ÷ 1.18 = ₹296.61
Vendor CP ₹296.61 → OK · ₹236.69 → MISMATCH

Myntra · Goddess (Use Vendor CP)

For tagged items (e.g. RENEE Goddess perfume) the vendor's stated cost is authoritative: validation accepts it (no mismatch) and the D365 Unit Price is written from the vendor CP.

Myntra's Goddess line ships at the vendor's CP as-is — the engine doesn't force the standard margin.
Swiggy · Status filter Swiggy only

Only CONFIRMED POs are punched. Any other status (COMPLETED / EXPIRED / CANCELLED / PENDING) is dropped from the run — with a named notification per PO on Warnings (never silent). Re-upload if a dropped PO should be punched.

A PO marked COMPLETED → ignored + warned: “PO STATUS COMPLETED — IGNORED (not CONFIRMED); dropped.”
Swiggy · NFS → For-Sale Swiggy only

Some fragrances have two master items on one base EAN: <ean> = (NFS) Not-For-Sale and <ean>_FS = (FOR SALE). Swiggy sells the For-Sale variant and the deal price sits on the _FS EAN, so a Swiggy line landing on the NFS item is remapped to its _FS twin — the deal then applies. Noted per line (never silent).

Bloom 8ML: EAN …674 (NFS, item 200076) → …674_FS (For Sale, 200075) → Swiggy deal ₹35 applies (was MISMATCH at ₹134.92).
EAN remap any marketplace

A punch's EAN is remapped to the correct master item (barcode changed / duplicate EAN) via the central Master Exceptions file.

Vendor EAN 8906121640885 → master 8906121640885_1 → resolves to the right item so the SO is correct.

These live in the engine config (Reliance) or the central Master Exceptions.xlsx / Swiggy Deal SKUs overlay — edit one place and every marketplace's output reflects it.

"Reliance" is five different customers that all print Reliance Retail Limited. The one reliable identifier on every PO is its Site code (Site : SAE7) — the unique per-DC code. Its namespace tells you online vs offline and the exact customer, so a PO can never be silently punched to the wrong entity or DC.

Rule: online = the Site code starts with S. Anything else (T8 / FR / TH / 6 / BAP) is offline and must not be uploaded into the online (20015) run.

Guard · Wrong channel live

An offline Reliance PO uploaded into the online (20015) run is blocked, not guessed — its Site code is checked against the offline customers' codes (read live from the mapping). Stops e.g. T8WL (Retail Indore) being silently punched as online 20015_2.

Guard · Ambiguous DC live

Online resolves by city today, so two DCs in one city collide (Gurgaon: Centro 122001 vs Farukhnagar 122506). A multi-DC city with an unmapped pincode is blocked, never defaulted. Pincode 122506 → Farukhnagar 20015_6 is mapped & correct.

Open items

2 Nagpur DCs (20015_3 / _4) share a city — capture their Site codes. FR49 is shared by Retail (20043_5) & Smart Bazaar (20615_7) — disambiguate.

5

Your decisions on a mismatch — drive the D365 dump

When a line is MISMATCH, you pick one on the review screen. The full SO Workbook always keeps every line; only the D365 dump reflects your choice.

Include as-is

Ship it with our computed price; you accept the difference.

Our CP ₹147.71, theirs ₹236.69 → D365 line uses ₹147.71.
Override set CP

Include it, but with the CP you enter (the box pre-fills with vendor's Their CP, editable).

You set CP = ₹236.69 → D365 line Unit Price = ₹236.69.
Exclude drop

Leave the line out of the D365 dump entirely (still in the full workbook for audit).

Vendor price clearly wrong → excluded; ERP never sees it.

The DB keeps the original forever: status=MISMATCH, diff, plus your action / override_cp / remark / decided_at — so you always know it was problematic and what you did.

✓

Upload SOP — applies to BOTH Online B2B & Offline · run every time you Process a PO

My personal pre-flight + post-check list, built from real past mistakes. Before processing, sanity-check the file; after recording, spot-check a couple of POs against the source.

① Before processing
1
Unit price — empty or override? Confirm whether the file actually carries a vendor Unit Price / cost (some channels send it, some don't — see §3 file formats). Decide up front whether the unit price should be left empty or overridden during upload. If it should have one and doesn't, the value & price validation will be wrong.
2
Ship-to — mapped or fuzzy? Every delivery location must resolve to a Ship-To (Cust No + ship-to code). Check whether it's an exact match or only a fuzzy / partial match — confirm it's the right destination. If a location is unmapped, fix it in Ship-To Mapping first, then upload.
3
Right sheet / location — don't mix. Upload each PO under its correct warehouse sheet — AHD POs in the AHD sheet, BLR in the BLR sheet — never mix them. DS POs go in DS and must be updated in the DS sheet, with the correct location.
4
Exception prices. Check whether deal / exception SKU prices are already baked into the unit price (Swiggy deals, vendor overrides — see §4 exceptions). Don't assume the flat marketplace margin applies.
② Keep current
5
Item master & MRP — refresh timely. Keep Item Master and item MRP up to date (the Hub shows a reminder at 15 days). Stale MRP → wrong price comparison on every line.
③ After recording — spot-check
6
Randomly pick 2–3 POs and open the source file side-by-side. Verify each: Qty · Total incl-GST value (GST amount included) · Ship-to (Cust No + code) and the address match the destination.
7
Randomly check 2–3 SKUs' count across all three: the dump → the D365 line → the marketplace portal. The quantity must match end-to-end.
④ Don't forget — staging
8
Run staging. Don't forget to run staging, including its M-Assist integration.
